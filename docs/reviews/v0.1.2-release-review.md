# Release review: v0.1.2 (in-app updater)

**Reviewer:** GPT-6.2 Astra, high effort, read-only, on `e0399ff` (`v0.1.1..e0399ff`).

**Outcome:** five rounds. Findings 2, 3, 4, 6, 7 and 8 and the issues raised in later rounds are fixed, apart from the deferrals listed at the end. Two issues were still partial after two fix attempts, so they were escalated; both were judged not critical and deferred past v0.1.2 (see `resolver-launch-record.md` and `resolver-image-inventory.md`).

| # | Severity | Finding | Outcome |
| --- | --- | --- | --- |
| 1 | Blocker | Install on quit never checked what was at the installed path, so it could swap out and delete an item that replaced the app after the update was prepared, or roll back a manual upgrade. | Fixed. The installed bundle's device and inode are recorded when the update is prepared. Install refuses if the path no longer holds that bundle, and after the swap it deletes the displaced item only if it is that bundle; otherwise it swaps back. Test: `installRefusesAStagedAppChangedAfterVerification`. |
| 3 | Should-fix | Turning off automatic updates did not stop an automatic download or a pending automatic install. | Fixed. Turning off automatic install cancels an automatic download, discards an automatic update that is ready, and install on quit skips an automatic update when the setting is off. Manual installs are unaffected. |
| 4 | Should-fix | Cancelling could skip the disk image detach, or still produce a ready update. | Fixed. Attach and detach run outside the cancelled task. Preparation checks for cancellation after detaching and discards the staged copy. Test: `cancellingAfterMountingDetachesAndLeavesNoStagedCopy`. |
| 5 | Should-fix | Startup cleanup in a second running copy treats the first copy's update work as abandoned. | Deferred, see below. |
| 6 | Should-fix | A failing automatic check stayed due and retried every hour; turning the check on after a recent check did not check. | Fixed. Automatic attempts are recorded when they start and count toward the daily interval. Turning the check on always checks once. |

| 8 | Nit | The feed accepted a tag without the `v` prefix, and a bundle version `0.2` passed for release `v0.2.0`. | Fixed. ## Round 1 deferrals

Both deferred cases fail safe: an update is dropped and the installed app keeps working. Nothing is deleted except OpenToolbox's own update work files.

- **#5, two running copies.** This needs two copies of the app running at the same time, which is unusual. The later copy's cleanup can remove the earlier copy's download, disk image mount or staged update. The earlier copy then fails to prepare, or skips installing on quit. Listed in the README's known limitations.
- **#7, silent failure on quit.** The install now refuses more cases on purpose (findings 1 and 2), and each refusal at quit leaves the current version in place. The app quits on the current version with no message, and the next launch removes the staged copy. Listed in the README's known limitations.

## Round 2

The re-check at `c87a792` marked 3, 4, 6 and 8 resolved and accepted deferral 7.

| Item | Re-check said | Change |
| --- | --- | --- |
| Finding 1 (partial) | The baseline was taken when preparation started, so an app replaced before the download, or changed in place, was adopted. | At launch, off the main actor, the app records its bundle's device, inode and birth time plus the SHA-256 of its whole main executable and `Info.plist` (`InstalledApp`). Preparation refuses before downloading unless the bundle still matches, and install checks again before the swap. After the swap, the displaced bundle must match the same record before it is deleted. The installed app is compared by bytes, not by signature validation, so a correctly installed app is never refused because of its signature. Tests: `prepareRefusesAnAppReplacedSinceLaunch`, `installLeavesAnInstalledAppChangedInPlaceAlone`, `installLeavesAReplacedDestinationInPlace`. |
| Finding 2 (partial) | The code directory hash covers one architecture, so a staged copy missing the other slice still passed. | The staged copy must also match the SHA-256 of the verified source's whole main executable and `Info.plist`. Test: `installRefusesAStagedAppMissingAnArchitecture` builds a signed two-architecture app, removes the other slice, requires that the code directory hash still matches, and checks that install refuses. |
| New: failed swap-back | A failed reverse rename threw the same error as a clean refusal and left the displaced item under the staged name, where startup cleanup deletes it. | The reverse rename's result is checked. If it fails, the displaced item is renamed to `OpenToolbox (moved aside …).app`, which cleanup never matches, and the error names its location. |
| Deferral 5 (not accepted) and new: image ownership | Detaching a device number from an earlier snapshot could eject a different image after the number was reused. Detach failures were ignored. | Each preparation holds an exclusive `flock` lease on its work folder (opened with `O_CLOEXEC`). Startup cleanup only touches folders whose lease it wins. Before each detach attempt, the device is looked up again from the image's path, and detach reports whether the image is gone. If it isn't, the update fails and the work folder is kept for the next launch's cleanup. Test: `workHeldByARunningCopyIsLeftAlone`. What remains of 5 is that a second copy running from the same folder removes the first copy's staged update at startup; it is listed in the README's known limitations. |

## Deferred past v0.1.2

- **Launch record bound by path (finding 1 remainder).** The record of the installed app is read by path just after launch, not tied to the running process. Not critical; see `resolver-launch-record.md`. Listed in the README's known limitations.
- **Image row without `image-path`.** Such a row is ignored, so cleanup can leave a hidden read-only mount until restart. Not critical; see `resolver-image-inventory.md`. Listed in the README's known limitations.
- **Second copy from the same folder (finding 5 remainder).** A second running copy removes the first copy's staged update at startup; Check for Updates… downloads it again. Listed in the README's known limitations.
- **`.pending-` work folder.** A crash between creating a work folder and renaming it leaves an empty folder with a lock file that cleanup never removes.
- **Path canonicalisation at the root.** `resolved(_:)` returns its input unchanged when no ancestor below `/` exists, so a trailing slash or a relative path survives. The updater's own paths always have an existing ancestor below `/`.
